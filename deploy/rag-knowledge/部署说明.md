## 零、先回答那个问题：升级时覆盖还是删除重传？

### 结论：**只覆盖 jar，绝对不要删目录**

原因很简单 —— **你的知识库不在 jar 里，它在 jar 旁边的 `data/` 目录里。**

```
rag-knowledge/
├── rag-knowledge-0.0.1-SNAPSHOT.jar   ← 代码，随时可以换
├── data/knowledge-base.json           ← ★ 知识库本体（已入库文档 + 向量）
├── config/application.properties      ← ★ 你的 Key 和端口
└── static/                            ← 可选，外置页面
```

`data/knowledge-base.json` 里存着所有已入库的段落**和它们的向量**。
删目录重传 = 这些全没了，你得重新上传文档，**重新烧一遍 Embedding 的额度**算向量。

### 三种做法对比

| 做法 | 结果 |
| --- | --- |
| ✅ **只覆盖 jar**（推荐） | `data/` 和 `config/` 原封不动，知识库完好 |
| ⚠️ 删目录再传整个包 | **知识库丢失**，除非你先把 `data/` 备份出来再放回去 |
| ❌ 上传整个包覆盖（含 config/） | 你的 Key 和端口配置会被包里的模板覆盖掉，得重新填 |

### 但"只覆盖 jar"也不够，必须**先停服务**

两个原因，第二个很多人不知道：

1. **上传过程中可能读到写了一半的文件** —— 20MB 的 jar 覆盖时，正在运行的进程
   按需读取 jar 内的类，可能读到损坏内容；
2. **就算覆盖成功，运行中的进程用的还是旧代码** —— Linux 上文件被替换后，
   进程仍然持有旧文件的 inode，内存里跑的还是老版本。**不重启 = 没更新**。

### 推荐流程（三种，按你的情况选）

**方式 A：从 v1 升级上来（最省事，推荐）**

如果你已经在 `/www/wwwroot/rag-knowledge` 跑着 v1，用 `upgrade-install.sh`。
它**只换 jar 和脚本，绝不动 `data/` 和 `config/`**：

```bash
# 1. 上传新 zip 覆盖旧的（覆盖 zip 本身无害）
# 2. 解压到临时目录（不要直接解压覆盖到 /www/wwwroot/）
cd /www/wwwroot
unzip -o rag-knowledge-deploy.zip -d /tmp/rk-new

# 3. 一条命令更新
bash /tmp/rk-new/rag-knowledge/upgrade-install.sh /www/wwwroot/rag-knowledge
```

脚本会：备份 `data/`+`config/` → 停服 → 保留旧 jar 以便回滚 → 换新 jar →
更新启停脚本 → **补上源文档**（`data/source/*.md`）→ 启动 → 体检。

**`config/application.properties` 只在目标完全没有配置时才补模板，已有配置绝不覆盖。**

**方式 B：用宝塔文件管理器（手工，仅供了解）**

```
1. 宝塔 → 文件 → 进入 jar 所在目录
2. 先备份：对 data/ 目录右键 → 压缩成 zip（下载下来更保险）
3. 停止服务（宝塔「Java 项目」面板点停止，或终端执行 ./stop.sh）
4. 上传新的 jar，同名文件选「覆盖」
5. 启动服务
6. 看日志确认：tail -f logs/app.log   或   ./status.sh
```

> ⚠️ 手工操作时**不要**把整个 zip 解压覆盖到 `rag-knowledge/`。
> 解压不会删除 `data/knowledge-base.json`（zip 里没有这个文件），
> 但会**覆盖掉你填好的 `config/application.properties`**，Key 就没了。

**方式 C：已经有了新 jar，只要替换**

```bash
cd /www/wwwroot/rag-knowledge
chmod +x *.sh          # 第一次需要
./upgrade.sh /tmp/rag-knowledge-0.0.1-SNAPSHOT.jar
```

出问题可以回滚（脚本结束时会打印具体命令）：

```bash
# 回滚代码
mv backups/rag-knowledge-0.0.1-SNAPSHOT.jar.<时间戳>.bak rag-knowledge-0.0.1-SNAPSHOT.jar
./restart.sh

# 回滚代码 + 数据
tar -xzf backups/backup-<时间戳>.tar.gz
./restart.sh
```

### 三种方式怎么选

| 你的情况 | 用哪个 |
| --- | --- |
| 服务器上已经跑着 v1，目录和配置都在 | **方式 A** |
| 只拿到了新 jar，没拿到新包 | 方式 C |
| 想手工一步步来 / 排查问题 | 方式 B |

## 一、包里有什么

```
rag-knowledge/
├── rag-knowledge-0.0.1-SNAPSHOT.jar    应用本体（内嵌 Tomcat，无需额外装容器）
├── config/
│   └── application.properties          ★ 外置配置，改完 restart.sh 即可，不用重新打包
├── data/
│   └── source/                         10 份源 Markdown，用于重建知识库（见第四节）
├── static/                             可选的外置页面目录（现在只有说明，见第五节）
├── start.sh / stop.sh / restart.sh / status.sh     Linux 服务器用
├── backup.sh                           备份知识库与配置
├── upgrade.sh                          已经拿到新 jar 时用它替换
├── upgrade-install.sh                  ★ 从 v1 升级上来时用它（见零、方式 A）
├── start.bat / stop.bat                             Windows 本地测试用
└── 部署说明.md                          本文件
```

**不需要装 Tomcat、不需要装 Maven** —— Spring Boot 打的是可执行 fat jar，内置了 Tomcat。

## 二、首次部署

### 1. 装 JDK 17

宝塔 → 软件商店 → 搜「Java 项目」→ 安装（会一并装好 JDK 17）。
或者手动装：`/www/server/java/jdk-17/`。

确认：
```bash
java -version    # 要看到 17.x
```

> ⚠️ 必须是 **JDK 17 或更高**。Spring Boot 4 要求 Java 17+，用 JDK 8 启动会直接报
> `UnsupportedClassVersionError`。

### 2. 上传

把整个 `rag-knowledge` 目录传到服务器，例如 `/www/wwwroot/rag-knowledge/`。

### 3. ★ 填 Key（这一步不做，上传文档和提问都会失败）

编辑 `config/application.properties`，把这两个填上：

```properties
ai.api-key=${AI_API_KEY:sk-你的DeepSeek密钥}
ai.embedding-api-key=${AI_EMBEDDING_API_KEY:你的智谱密钥}
```

冒号后面就是默认值，填进去就能用。**这两个 Key 不一样，是两套独立的服务**：
- `ai.api-key` → DeepSeek，负责「改写问题」和「依据片段作答」
- `ai.embedding-api-key` → 智谱，负责「向量化」

更推荐的做法是用环境变量（宝塔「Java 项目」面板里有环境变量配置项），
这样 Key 不出现在文件里：

```
AI_API_KEY=sk-xxx
AI_EMBEDDING_API_KEY=xxx
```

### 4. 给脚本执行权限

```bash
cd /www/wwwroot/rag-knowledge
chmod +x *.sh
```

### 5. 启动

```bash
./start.sh
./status.sh        # 等十几秒后看状态
```

或者用宝塔「Java 项目」面板配置：
- 项目路径：`/www/wwwroot/rag-knowledge`
- jar 文件：`rag-knowledge-0.0.1-SNAPSHOT.jar`
- **工作目录：必须是 jar 所在目录**（否则读不到 `data/` 和 `config/`）
- 启动参数：`--spring.config.additional-location=optional:file:./config/`
- 端口：`8081`

> **工作目录这一项最容易踩**。`kb.store-path=data/knowledge-base.json` 是**相对启动目录**的，
> 工作目录设错了会读不到知识库，表现是"重启后知识库空了"（其实没空，只是读错了地方）。

### 6. 放行端口

宝塔 → 安全 → 放行 `8081`。云服务器还要去控制台的安全组放行一次。

访问：
- 知识库：`http://<服务器IP>:8081/`
- 检索评测：`http://<服务器IP>:8081/eval.html`

## 三、目录里哪些能动、哪些不能动

| 路径 | 能不能删 | 说明 |
| --- | --- | --- |
| `rag-knowledge-*.jar` | 能（但要立刻放新的） | 代码，随时可换 |
| `data/knowledge-base.json` | **绝对不能** | 知识库本体，删了就没了 |
| `data/source/` | 能 | 源文档，只是为了方便重建，删了不影响运行 |
| `config/application.properties` | 不能 | 你的 Key 在这 |
| `logs/` | 能 | 日志，可以定期清 |
| `backups/` | 能 | 备份，确认新版本没问题后可以清旧的 |
| `app.pid` | 能 | 进程号，服务没在跑时删掉无妨 |

## 四、知识库怎么建

包里的 `data/source/` 有 10 份 Markdown（SpringBoot / Spring核心 / SpringMVC / Spring Security /
微服务 / Spring Cloud Alibaba / MyBatis / MyBatis-Plus / MySQL / Redis，共 1.8 万字）。

**方式一：在页面上传**（最简单）
1. 打开 `http://<IP>:8081/`
2. 把 `data/source/*.md` 拖到「知识库」区域的拖拽框里（支持多选）
3. 每份文档会按 Markdown 标题自动切成章节入库

**方式二：命令行批量导入**
```bash
for f in data/source/*.md; do
  name="$(basename "$f" .md | sed 's/^[0-9]*-//')"
  curl -s -X POST "http://127.0.0.1:8081/kb/upload-file" \
    -F "file=@$f" -F "source=$name"
  echo ""
done
```

入库后打开页面能看到「段落 124 ／ 文档 10」，提问时命中片段会显示三级章节路径，
比如 `9. MySQL 知识库 > 5. 索引（高频重点） > 索引失效常见场景`。

> 💡 **换 Embedding 模型后向量维度会变**，旧向量会被自动跳过（日志里有告警）。
> 这时需要在页面「清空知识库」后重新导入。

### 从 v1 升级上来的知识库怎么办

如果你服务器上已经跑着 v1（`dist/rag-knowledge-deploy`），旧知识库是能直接读的 ——
v2 兼容 v1 的落盘格式（v1 没有 `section` 字段，读进来后按「无章节」处理），**不会报错**。

但建议**重建一次**，因为：

| | v1 的知识库 | 重建后 |
| --- | --- | --- |
| 段落数 | 118 | 124 |
| 文档数 | 1（全叫「手动粘贴」） | 10（每份文档能单独删） |
| 章节路径 | 全部为空 | 三级路径，如 `MySQL-知识库 > 5. 索引（高频重点） > 索引失效常见场景` |
| 重复内容 | 有一份完整的重复文档 | 已去重 |

重建步骤：

```
1. 页面 → 「清空知识库」
2. 把 data/source/*.md 全部拖进上传框（或用第四节的命令行批量导入）
```

**代价**：124 个块的 Embedding 调用（智谱额度）。**收益**：命中片段能定位到具体章节，
面试演示时这一点非常直观。

> ⚠️ 清空前建议先 `./backup.sh`。旧知识库删了就找不回来了。

## 五、改前端页面不用重新打包

`config/application.properties` 里已经打开：

```properties
spring.web.resources.static-locations=file:./static/,classpath:/static/
```

意思是：**优先读 jar 同级的 `static/` 目录，找不到才回退到 jar 内置的页面**。

所以改页面只要：

```bash
mkdir -p static
# 把改好的 index.html / eval.html 上传到 static/
# 浏览器 Ctrl+F5 强刷，不用重启
```

想恢复成 jar 内置的版本，把 `static/` 里的文件删掉即可。

## 六、排查

| 现象 | 原因 / 处理 |
| --- | --- |
| 启动报 `UnsupportedClassVersionError` | JDK 版本不够，要 17+ |
| 启动正常但页面打不开 | 端口没放行（宝塔安全 + 云控制台安全组都要放行） |
| 重启后知识库"空了" | **工作目录不是 jar 所在目录**，读不到 `data/` |
| 上传文档报"未配置 Embedding API Key" | `config/application.properties` 里的 `ai.embedding-api-key` 没填 |
| 提问报"未配置对话模型 API Key" | `ai.api-key` 没填 |
| 提问报 `Embedding 接口返回错误(401)` | 智谱 Key 不对或过期 |
| 上传文档很慢 | 正常，每段都要调一次 Embedding 接口；125 个块约 1~2 分钟 |
| 想看实时日志 | `tail -f logs/app.log` |
| 想确认服务活着 | `./status.sh` |

## 七、性能与资源

- **内存**：`-Xmx512m` 足够（124 个块约 3MB 向量）。1GB 内存的小机器可以把
  `start.sh` 里的 `JAVA_OPTS` 调成 `-Xms64m -Xmx320m`
- **磁盘**：jar 约 20MB + 知识库约 3MB（可按知识库规模线性估算：
  每 1000 个块大约占 25MB）
- **CPU**：检索本身是纯内存计算（124 个块的全量余弦约 5ms），瓶颈在网络
  （改写 1.4s、生成 0.7s），所以**单核也能跑**
- **首次启动**：约 10~30 秒

## 八、关于评测

`http://<IP>:8081/eval.html` 是检索评测页，可以跑消融实验看每一层的收益。

**注意**：评测跑的是纯检索（不调用大模型），但**会调用 Embedding 接口**。
跑一次完整消融（40 条用例 × 6 档位）大约消耗 240 次 Embedding 调用
（有缓存，实际约 40~80 次）。对自己的额度有影响的话，可以先跑 `quick` 模式（2 档，十几秒）。

服务器上一般不需要跑评测 —— 那是开发和调参时用的，结论已经写在
`docs/评测与调参.md` 里了（源码工程中）。
